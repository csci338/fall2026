# Programming Readiness Bundle: Instructor Guide

These materials support an instructor-facing specifications-grading process. The required **Programming Readiness Bundle** contains six binary specifications, R1–R6. Record each specification as **Satisfactory** or **Not Yet**. Do not assign points, percentages, partial credit, or averages. Once a specification is Satisfactory, bank it; students reassess only specifications currently marked Not Yet.

## Administration timeline

| Date | Event | Purpose |
| --- | --- | --- |
| August 27 | Verification attempt 1 | Individually verify R1–R5 on paper. Bank Satisfactory specifications and prescribe targeted modules for Not Yet results. |
| September 10 | Verification attempt 2 | Reassess only Not Yet specifications using a secure alternate form; retain all previously banked results. |
| September 24 | Final team-eligibility verification | Reassess remaining Not Yet specifications using a secure alternate form and complete any due typed follow-up for R5/R6. |

Keep the distinction explicit: **practice** gives actionable feedback; **verification** produces bankable Satisfactory/Not Yet records. These three dates are the announced verification opportunities. If an additional reassessment is approved, announce its date, eligible specifications, and form before the attempt.

## Standard paper conditions

- Allow 40–50 minutes.
- Require phones, watches, earbuds, laptops, tablets, notes, and other devices to be put away.
- Allow only the provided [Java reference sheet](java-reference-sheet.md), writing tools, and instructor-provided paper.
- Students work independently. Clarify wording, but do not coach an algorithm or confirm an answer.
- Collect all prompts, scratch paper, and reference sheets before students leave.
- Apply documented accommodations, including extended time, reduced-distraction location, assistive technology, breaks, or an alternate response format. Preserve the same specifications and individual-verification purpose; coordinate through the institution's established accommodation process.

## Scoring and records

Use the [specifications rubric](specifications-rubric.md) one specification at a time.

1. Mark each attempted specification **Satisfactory** or **Not Yet**.
2. Record a short evidence note for every Not Yet result.
3. Prescribe a focused practice module and action with the [module prescription template](module-prescription-template.md).
4. Bank all Satisfactory specifications across later attempts.
5. At reassessment, present only the student's Not Yet specifications (plus any required alternate integrity check).
6. Mark **Programming Readiness Bundle complete** only when R1–R6 are all Satisfactory. Do not average across specifications or substitute strength on one specification for another.

Use [tracker-template.csv](tracker-template.csv) for the private instructor record. Keep assessment records in the approved course record location and limit access to instructional personnel with a legitimate need.

## Typed follow-up

After a paper verification, assign [typed-follow-up.md]. Return or display only the student's collected response long enough for transcription as locally appropriate; do not release a reusable blank secure form. The student types one collected paper solution into the supplied harness, runs tests, logs corrections, and explains one revision. Evaluate the follow-up as R5/R6 evidence. A paper algorithm that was Not Yet does not become Satisfactory merely because the harness later passes; require the prescribed reassessment for that paper specification.

## Security and alternate forms

- Use Forms A, B, and C as an assessment bank, not as public practice material.
- Rotate forms and use a different form for reassessment when practical.
- Keep answer keys separate from student copies. Before printing, remove the key pages or print only through the `End of student form` marker.
- Number copies when useful; collect every copy and destroy scratch work according to local records practice.
- Do not discuss exact secure prompts with students who have not completed that administration.
- If a form is exposed, retire it from verification use and create an equivalent alternate using the same specification criteria.

## GenAI and authorship verification

The paper verification is the primary observed evidence of individual programming readiness. Generative AI, code-completion systems, chatbots, and online search are not allowed during observed paper or typed verification unless an approved accommodation explicitly requires a tool and equivalent controls are arranged.

Do **not** use AI detectors to infer authorship or misconduct. They are not reliable evidence. If submitted work and observed paper performance differ materially, use a neutral follow-up: ask the student to trace, explain, test, or revise comparable code under observed conditions. Record the demonstrated specification result, not a detector score. Follow applicable course and institutional processes for any separate academic-integrity concern.
